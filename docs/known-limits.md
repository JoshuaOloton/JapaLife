# Known limits of the current build

Moved out of CLAUDE.md, which links here. The rules these entries imply for new code are summarised in CLAUDE.md under "Rules from the build"; this file has the full reasoning.

Things that are deliberately incomplete or that will bite later. Remove an item when it is fixed.

## Ledger and money (`apps/server/src/economy/`, `packages/db`)
- **Game code calls `WalletService`, never `Ledger`.** `WalletService` (`apps/server/src/economy/wallet.ts`) has `getBalance`, `credit` (faucet reasons only), `debit` (sink reasons only) and `transfer`. `getBalance` is a snapshot: never check it and then spend, call `debit`, which checks under a lock. Idempotency keys must be derived from the event (`shift:<playerId>:<shiftId>`), never random per call, or a retry pays twice.
- **`transfer` exists but is server-internal.** No client intent reaches it, it charges no fee and has no limits. Do not expose it until the "Money sharing controls" decisions are made.
- **Only `Ledger` writes `Transaction` rows.** The "player balance never goes negative" rule cannot be a database CHECK (system wallets legitimately go negative), so it is enforced by `Ledger.applyMovement` under the wallet lock. Any code that creates `Transaction` rows another way (raw SQL, `prisma.transaction.create`) bypasses it. Don't.
- **Hot-row bottleneck.** Every earn locks the single `faucet` system wallet, and every spend locks the single `sink` wallet (one pair per currency), so all earning serialises across the whole game. Fine for single-player and early multiplayer. Fix before real load: shard system wallets (e.g. `faucet:0..N`, chosen by hashing the player id) and re-run the concurrency tests.
- **Balance cap.** `MAX_WALLET_BALANCE` is 10^15 smallest units (about 10 trillion naira), kept below `Number.MAX_SAFE_INTEGER` so balances can travel as JSON numbers. A database CHECK mirrors it. The `sink` wallet's running total only ever grows, so it also hits this ceiling eventually; sharding or rotating system wallets (per season) fixes that too.
- **Conversion is not persisted.** `convertAmount` (integer maths, rounds down, refuses zero results) is built and tested, but there is no `convert()` operation yet. It must write both legs through the `fx` system wallets plus a `Conversion` row in one transaction, locking up to four wallets in sorted order. Phase 3.
- **Reasons are names only.** `FAUCET_REASONS` and `SINK_REASONS` in `packages/shared/src/economy.ts` now cover living costs, documents, UK and Canada immigration fees (`VISA_FEE_REASONS`), departure, family, and scam traps. No amounts are in code: every fee, wage and price must come from `content/` with a `source` URL and an `asOf` date, and the real 2026 fee values still need to be researched and entered there. Add new faucets and sinks to that file (no migration needed, since `reason` is a string). The cost is that the database does not enforce the list. Currency conversion legs and player-to-player transfers are neither faucets nor sinks and need their own reason class when built.
- **Earn rate limit is built** as a per-job daily shift cap (`maxShiftsPerDay`, reset at midnight Lagos time) plus a per-client intent token bucket.
- **Abnormal-balance flagging (decided 2026-10-16: record only, no automatic penalty).** `BalanceWatch` (`apps/server/src/economy/balanceWatch.ts`) runs every 10 minutes and sums what each player received per ledger reason over the last 24 real hours, then compares it with `earningCeilings`, which derives the most the rules in `content/` allow (scaled by the `GAME_CLOCK` speed). Over-ceiling sums become `BalanceFlag` rows (one per player, currency, reason and Lagos day, keeping the worst amount) and a log line with no amounts. **Every reason without a ceiling has a ceiling of zero**, including `player_transfer` and future conversion legs: when you add a faucet, add its ceiling in `earningCeilings` or every use of it is flagged. There is no moderator view yet. The scan filters `Transaction` by `createdAt`, which has no index of its own (only `[reason, createdAt]`): fine now, add an index (a ledger schema change, so ask) before real load. In dev, the seeded test player is flagged for `starting_balance`, since it gets both the seed and the normal starting balance.
- **The ledger is append-only.** A trigger blocks UPDATE and DELETE on `Transaction`. Correct a mistake with a reversing entry, never an edit. Only tests TRUNCATE.
- **Money is `bigint`.** `JSON.stringify` throws on bigint. Send balances to the client as numbers (safe under the cap) or strings, and never do money maths in `number`.
- **No loans.** Player wallets cannot go negative, so credit, overdrafts, student loans and mortgages need their own liability model, not a negative wallet.

## Server and protocol
- **Dropped connections reconnect by themselves (2026-10-22).**
  - **Why:** standing still on the vivo Y29 lost the connection for good. The likely cause is the screen timing out, at which point Android suspends the page's network. The server removed the player the moment the socket dropped, so the client had nothing to come back to.
  - **Server** (`DistrictRoom`):
    - `onDrop` keeps the place for 5 minutes (`allowReconnection`), stops the player walking and stops toasts (the inbox keeps them).
    - `onReconnect` restores the `StateView`, re-subscribes notices, runs the catch-up and sends fresh stats.
    - A fresh join by the same player while dropped (a reload) gives up the kept place instead of being refused "already connected".
  - **Client** (`useDistrictConnection`):
    - Shows "Reconnecting..." while the SDK retries (60 tries, backing off to every 5 s, about five minutes).
    - If it gives up, it joins afresh when the page is next visible, or on "Try again".
  - **Not done:**
    - Keeping the screen awake while playing. The Screen Wake Lock API needs HTTPS, and phones load the game over plain http on the LAN, so it waits for HTTPS (like web push).
    - Messages sent while dropped (a toast, an `interaction` reply) are lost. The inbox and the fresh stats on reconnect cover what matters.
  - Tested in `DistrictRoom.test.ts` by dropping a socket on the server with close code 4010.
- **Every intent goes through `parseIntent`** in `DistrictRoom`'s single `onMessage("*")` handler, then through a per-player `KeyedMutex` so one player's intents run in order. Never add a message handler that skips either. The mutex is in-process: with several server instances it needs a database or Redis lock (Phase 5).
- **No auth (dev identity stub).** A client names itself with the `playerId` join option, accepted only when `NODE_ENV` is not `production`; in production nobody can join. Anyone can pose as anyone in dev. Auth, the 18+ gate and data-protection decisions need your approval before they are built.
- **Game state is in Postgres, not the room.** `PlayerState` (meters, rent due date, event check time), `Shift` and `EventFiring` hold everything that must survive a restart; rooms only hold positions. Hunger and energy are computed from a stored value plus elapsed real time.
- **Logging goes through `logError`** (`apps/server/src/log.ts`). It keeps only the class and code of Prisma errors, because their messages can echo query arguments (player ids, amounts, references). Never `console.error(error)` directly.
- **Scheduled jobs:** `startGameLoop` (every 30 s) pays finished shifts, expires unanswered requests and charges late rent fees for everyone, online or not. `startBalanceWatch` (every 10 min) raises balance flags. Random events are only evaluated for connected players (every 60 s, and caught up once on join).
- **Inbox (decided 2026-10-17).** Every notice to a player goes through `InboxService.deliver` (`apps/server/src/game/inbox.ts`): it stores an `InboxMessage` row and shows a toast if the player is connected. Never tell a player something with `client.send` or `NoticeBus.publish` directly, or an offline player never sees it. A notice a connected player saw as a toast is stored already read, so the HUD's unread badge counts only what they missed; the join catch-up runs before the toast subscription, so whatever happened while away lands as unread. The `openInbox` intent returns the latest 50 and marks them read. The text is stored as shown at the time (later copy changes do not rewrite old messages), and only the latest 50 per player are kept. No push or email yet, so a player only finds out by opening the game.
- **Power cuts and price rises are per player** in Phase 1 (stored per player), not per district. Revisit in Phase 5 when players share a district.
- **Unpaid rent costs late fees (decided 2026-10-17).** After the 3-day grace period, a late fee (N4,000, `rent.lateFee` in `ngn.json`) and -5 morale, then again every 7 days until the rent is paid. A player who cannot pay a fee is charged nothing and loses 10 morale instead (wallets never go negative). The next fee time is `PlayerState.lateFeeDueAt`; each fee is claimed by moving it on with a conditional update before the debit (reference `rent_late:<player>:<dueAt>`), so the room and the game loop cannot charge it twice, and a crash between claim and debit loses a fee in the player's favour. Paying rent resets it to the new due date plus the grace period. A player away for months comes back to every missed fee at once; there is no cap and no eviction yet. Eviction (and a credit-score effect abroad) replaces endless fees later, once housing is a system.
- **No intent for the bus stop.** It exists in `lagos.json` and answers `interact`, but nothing can be ridden yet; the bus fare is config only. The fuel station sells generator petrol through `buyItem` (`ShopService`).
- **Food and shop purchases use a random reference per intent** (`food:<player>:<uuid>`, `shop:<player>:<uuid>`). A crash after the debit but before the meter update would charge without feeding (or fuelling). Rare, and safe in the player's disfavour only by one purchase; fix by recording purchases in a table first if it ever matters.
- **The generator tank limit is checked outside the wallet lock,** relying on the per-player `KeyedMutex`. Money is always safe (the ledger locks), but two purchases that bypass the mutex could overfill the tank.
- **Capacity queue is a stub.** `CapacityQueue` (`apps/server/src/game/capacityQueue.ts`) holds a line with positions and is tested, but is not connected to matchmaking. Colyseus already refuses joins beyond `MAX_PLAYERS_PER_ROOM`, so nothing over capacity is accepted.
- **One district.** `DistrictRoom` always hosts `yaba`.
- **Collision is one shared function (decided 2026-10-15).** `moveWithCollisions` in `packages/shared/src/collision.ts` stops the player at building footprints and the district edge. The server runs it as the authority; the client runs the same code to predict its own walking, so they agree and there is no rubber-banding. Buildings are defined once in `content/cities/<city>.json` (`buildings`, `roads`); the client draws them from those numbers and receives them in the `district` message on join. `loadContent` refuses to start if a spawn or location is inside a building, a building sticks out of the district, or any location cannot be reached on foot from the spawn point (`checkLayout.ts`). **Since Slice 11c the walls are `districtObstacles(layout)`**: buildings, the blocking part of each prop, and a 0.6 m box per standing NPC. The server (`DistrictMap`), the client's prediction (`Player.tsx`) and `checkLayout` all use it; never pass `district.buildings` as the boxes, or the client and server disagree at the first generator. `checkLayout` also refuses a blocking prop or NPC on a road, a prop of an unknown kind, and a `wire` with one pole.
- **Collision checks go through a spatial grid (Slice 11h-1, 2026-10-22).**
  - `isBlocked`, `moveWithCollisions` and `reachableTargets` take `Obstacles`, a `SpatialGrid` of 8 m cells (`packages/shared/src/spatialGrid.ts`), built once with `obstacleGrid(districtObstacles(layout))`. They no longer accept a box list, so the type system stops anything from scanning every obstacle on each step, which would not scale to Big Yaba.
  - The grid answers exactly as testing every box would, including at a wall's face (a hair of slack only adds candidates); `spatialGrid.test.ts` checks this on random layouts.
  - `reachableTargets` (server start) also keeps to typed arrays and looks only at the cells near each target. On a 600 m stand-in city it takes about 40 ms against about 2 s before, and about 115 ms at 1 km.
  - Not on the grid, on purpose: the nearest-place checks (`DistrictMap.nearest`, the client's `nearestPlace`) and `checkLayout`'s road checks. They loop over places and roads, which number tens even at 600 m, not thousands. Revisit if a district gets hundreds of places.
- **Rapier is not used for player movement.** Running a second physics engine on the client would disagree with the server's collision and cause snapping, and its WASM adds download and CPU cost on low-end phones. `@react-three/rapier` stays installed for later non-authoritative effects (props, ragdolls); it is not part of the walking path. Revisit if buildings stop being axis-aligned boxes.

## Content
- **Yaba is generated (Slice 11h-2, 2026-10-22).** `pnpm city` (`apps/server/src/generateCity.ts`, logic in `apps/server/src/city/`) writes `content/cities/lagos.json` from `content/cities/plans/lagos/` (`city.json` plus `yaba.json`).
  - What the plan holds:
    - streets with a class (`main` 8 m, `inner` 6 m, `lane` 4 m and walk-only);
    - which building types line each class, with market zones that change the mix;
    - hand-placed landmarks, with positions relative to their anchor and a `clear` area kept free of generated things;
    - the traffic fleet and bus stops.
  - What the generator places:
    - poles with wires between junctions;
    - speed bumps on main roads;
    - buildings facing every street;
    - generators and trees in the gaps between buildings;
    - scattered trees;
    - two lanes on each main and inner street (on the right);
    - walkways at the road edges.
  - It is seeded, and a test fails if `lagos.json` differs from what the plan generates.
  - The old 120 m Yaba is the `yaba-junction` landmark, unchanged except that the face-me-face-you house's footprint went from 5.05 to 5.0 m. It had reached 5 cm into Herbert Macaulay Way, which the new "building on a road" check caught.
  - `checkLayout` now also refuses a building on a road and two buildings that overlap.
- **Yaba's street plan is stylised, not surveyed (decided 2026-10-21).** It uses real street names on a straight grid, not OpenStreetMap data, whose ODbL licence would make us share our city data under the same licence.
  - Positions are approximate. Murtala Muhammed Way runs along the east edge (moved there 2026-10-22 at the owner's word; its fuel station moved with it).
  - Ojuelegba Road and Iwaya Road were added as the two inner north–south streets. They are real Yaba-area roads, but placed loosely.
  - Business names are generic (Yabacon Hub, Sabo Plaza). The mosque is a placeholder: a white box and a green minaret box, until a Blender model is made like 11f's buildings.
  - Main roads stay 8 m with one lane each way, not the 4 lanes the 11h plan first said, so the old centre and its poles stay as they were.
- **Phase 1 numbers are placeholders.** Everything in `content/economy/`, `content/events/` and `content/cities/lagos.json` is marked `"basis": "game-balance"` instead of a `source` URL: starting balance, rent, food prices, shift pay, event amounts and frequencies are tuning guesses, not researched Lagos prices. Retune them after play-testing. Real rules (Phase 2) must use `source` plus `asOf`.
- **Copy (decided 2026-10-17): plain English with light Nigerian touches** ("chop", "wait small", "NEPA has taken light"); the flavour comes from specifics, not heavy Pidgin. A Pidgin version would be its own language file (`pcm.json`), not a mix. The client bundles `en.json` at build time (the welcome screen needs it before connecting), so changing copy needs a rebuild, not a code change. The browser imports it from `@japalife/shared/copy`, which has no zod, so the first download stays small; the schema runs at server boot and in `pnpm test`. Only English exists, and nothing picks a language yet.
- **Action prompts:** the button at a place shows its `prompt` from the city file ("Buy food at Mama Put"), or its kind's template from `copy/en.json` ("Work a shift at {place}").
- **Content is loaded once at boot** by `loadContent()` and handed to the game systems. Unknown fields are rejected, and cross-references (job sites, food vendors, fuel station items, event files per `GAME_EVENT_IDS`) are checked.
- **Meters (decided 2026-10-15, extended 2026-10-16):** hunger drains 4 points an hour, so a 45-point meal lasts about half a real day; a meal (the whole order) is refused with `already_full` if it would fill hunger more than `overeatAllowance` (10) past 100, so a full player cannot keep eating or farm morale from food (decided 2026-10-17); energy regenerates 6 an hour; morale drifts 1 an hour back towards 60, food lifts it, and events can lower it. Below 30 morale, energy recovers at half speed and a shift started then pays 80% (the pay is fixed on the `Shift` row when it starts). All in `content/economy/needs.json` and `content/events/`, marked TODO for tuning.
- **Power cuts (changed 2026-10-16):** they now last 6 hours and **no longer block work** (`blocksShifts: false`: offices run their own generators). Their effect is at night (19:00–06:00 Lagos, `night` in `lagos.json`): energy recovers at 25% unless the player's generator has fuel, which it burns only while it is both night and dark. Petrol costs N900 a litre and runs it 2 hours; the tank holds 12 hours. Morale -3 per cut.
- **Price rises (changed 2026-10-16) are permanent and compound:** about once a month, +3% on food. There are no pay rises yet, so over months of real time prices outrun wages. That needs pay rises (or job progression) before launch.
- **Black tax is a choice (decided 2026-10-17).** It no longer takes money: it creates an `EventChoice` row (amount, which `asks` text, a 48-hour `expiresAt`) and the HUD shows a card. Paying debits exactly the amount (reference `event:<choiceId>`) and raises family; declining costs morale and family, less if the player could not have paid (`declineBroke`); an unanswered request expires as a decline. Every answer and expiry first claims the row with a conditional update (`answer` still null), so double taps, two tabs and the expiry job cannot settle it twice. Only one request waits at a time. The card shows the money, never the stat changes. Expiry runs on join, at the room's event check, and in the 30-second game loop (under the player's mutex). The request and its outcome go to the inbox, but with no push, a player who does not open the game for 48 hours still misses it: revisit the window when push exists.
- **Family relationship** (0-100, starts at 60) only changes through black tax so far, and nothing reads it yet. The Phase 4 family-reunion chain will.
- **Meters are computed by cutting elapsed time into segments** (`needsAt` in `apps/server/src/game/needs.ts`) wherever night, a power cut, the generator's fuel or low morale starts or stops, so offline time is simulated exactly. Every code path that changes a meter must go through `PlayerService.applyChange` or `saveNeeds`, which bring all meters up to `now` first.

## Tooling
- **Our own models are Python scripts run in headless Blender (11f, decided 2026-10-20).** `assets/blender/<name>.py` builds a model from simple parts with `bmesh` (Blender's mesh-editing API), painted from one shared palette sheet (`lib/kit.py`: 16 x 16 swatches; only ever add colours to the end of `PALETTE`, or every model built earlier changes colour). `pnpm blender [names]` runs them with `--background --factory-startup` and writes a GLB, a `.blend` to open in the Blender window, and a preview PNG to `assets/built/` (git-ignored); `pnpm assets` then compresses the GLBs like any pack. Models are in real metres (scale 1), face +z and stand on y = 0. Blender comes from `$BLENDER` or `/Applications/Blender.app` (5.2.2 LTS here). Hand edits made in the Blender window are lost on the next build unless they go back into the script.
- **Blender's glTF exporter drops texture coordinates that no texture uses (found in 11f-2).** A mesh whose UVs the game needs (the hair cap, which the game paints itself) must have an image texture in its material, even a 4 x 4 placeholder, or the GLB has no `TEXCOORD_0` and the painted pattern never shows. Check a new GLB's attributes when a texture "doesn't appear".
- **TypeScript is pinned to `~6.0`** because `typescript-eslint` does not support TS 7 yet. Revisit when it does.
- **`pnpm-workspace.yaml` `allowBuilds`:** `esbuild` is allowed; `prisma`, `@prisma/engines` and `msgpackr-extract` are declined. The first two are not needed (migrate and generate work). `msgpackr-extract` is an optional native speed-up for Colyseus with a JS fallback; revisit if message encoding shows up in profiling.
- **CI needs a Postgres service** for the ledger tests, and `DATABASE_URL` set.
- **Prisma 7's `migrate dev` does not regenerate the client.** After a schema change, run `pnpm db:generate` (or `pnpm install`), or the new models are `undefined` at runtime.
- **Client bundle (2026-10-16):** the page shell is ~175 KB gzipped; the game (three.js, R3F, Colyseus, zod) is a lazy `next/dynamic` chunk of ~335 KB gzipped. Whole first visit is ~470 KB over the wire. `pnpm budget` builds the client and fails above 15 MB, counting every static chunk, the HTML and `public/` (an upper bound: 1.85 MB raw, 0.53 MB gzipped on 2026-10-16; 1.86 MB raw on 2026-10-17 after the copy moved to content, which adds a ~4 KB gzipped chunk to the first visit while zod stays in the lazy game chunk). CDN city assets are outside the build and will need their own per-district budget. `@react-three/drei` and `@react-three/rapier` are installed but unused (drei's `Text` would download a font; signs are canvas textures instead).

## Client (`apps/client/game/`)
- **Walk by default, run on demand (decided 2026-10-18).** A partly pushed joystick walks (up to 1.8 m/s, `WALK_SPEED`), pushing it past 90% runs (4 m/s, the server's `PLAYER_SPEED_UNITS_PER_SECOND`); on a keyboard the keys walk and Shift runs (`gait.ts`, `input.ts`). The server knows nothing of gaits: walking is a shorter `move` direction, which it already scales by. The animation picks walk or run from the measured speed.
- **The camera always faces north** (no orbit). Up on the joystick or W walks away from the camera. A rotating camera needs a second touch control and has to rotate the input direction too; revisit if play-testers find it limiting.
- **Reconciliation is loose, not input-replay.** The server does not acknowledge move `seq`, so the client cannot replay unacknowledged inputs. Instead the prediction may lead the server by up to `MOVING_TOLERANCE` while walking, glides onto the server's spot when standing still, and snaps beyond `SNAP_DISTANCE` (`reconcile.ts`). Good enough for a non-competitive walk; revisit if players ever race or collide with each other.
- **Other players are not drawn** (Phase 1). `SnapshotBuffer` is ready for them: render each remote player at `sample(now - INTERPOLATION_DELAY_MS)`.
- **The touch joystick was play-tested on a vivo Y29 (2026-10-16) and felt fine.** It only appears on `(pointer: coarse)` devices.
- **FPS meter:** open the game with `?fps` (any build) for current fps, the lowest one-second fps and the longest frame after a 5 s warm-up, and the pixel ratio in use. Measure on a production build (`pnpm start:client`), since dev mode is slower. **Baseline (2026-10-16, vivo Y29, Chrome, production build): 60 fps (the screen's cap), low 60, worst frame 25 ms, dpr 1.50.** After Slice 11b (2026-10-19, character, four building models, painted ground, gutters, windows, day/night lighting): 60 fps, low 60, worst frame 34 ms (probably a one-off as a model first reaches the GPU). After Slice 11c (2026-10-19, props and NPCs): low 59, worst frame 40 ms, 24 draw calls, 20.9k triangles. Since 11c the meter also shows draw calls and triangles (`renderer.info`, budget < 80 calls). Since 11f-4 it pauses while the page is hidden (another app or the screen off used to count as one huge frame), and the worst frame says what the GPU had to set up during it, e.g. "worst 812 ms (+3 shaders, +1 textures)": new shaders mean a compile stall. Re-measure on the same phone after any change that adds visual cost. The meter sits in the HUD column under the chips, so it is never covered on small or landscape screens.
- **Use only APIs that work on plain http.** Phones open the dev and test builds at `http://<lan-ip>:3000`, which is not a secure context, so secure-only APIs (`crypto.randomUUID`, `navigator.clipboard`, service workers) are missing there and crash the page. Use `crypto.getRandomValues` instead of `randomUUID`.
- **Prices and pay reach the client in the `interaction` reply** (`describeOffer` in `apps/server/src/game/offers.ts`), computed with the same `priceWithRise` the purchase uses. The client has no copy of `content/`.
- **HUD countdowns use the server's clock** (the last `stats.serverTime` plus monotonic elapsed time), never the device clock. They tick at real speed between stats updates, so with `GAME_CLOCK` set they drift until the next update (at most 60 s, the event check).
- **The 18+ gate is a stub:** a self-declaration remembered in `localStorage`, no date of birth, nothing sent to the server, trivially bypassed. The real gate comes with sign-up (needs approval: auth and player data).
- **Server messages are buffered by `MessageBuffer`** (`connection.ts`) from the moment of joining, because stats arrive before React mounts the HUD and Colyseus drops messages with no handler. Register new HUD message types there, not with a late `room.onMessage`.
- **The character (Slice 11a, `game/character/`).** A Quaternius body (free tier, "superhero" build only), cloned per person, with hair re-bound to its skeleton by bone name. The body, hair and animations download after the game chunk; the capsule shows meanwhile, and for good if a download fails (`ModelBoundary`). Measured over the wire on a production build (2026-10-18): about 530 KB for the character, including both decoders. Four draw calls per person (body, eyes, eyebrows, hair; three when bald).
- **Customisation (Slice 11d).** A character is six catalog ids (`appearanceSchema`: body, skin tone, hair, hair colour, outfit, outfit colour), stored in `PlayerAppearance` (cosmetic, not personal data) and checked by `appearanceProblem` on the server. The catalog (`content/characters/catalog.json`) reaches the client inside the `DistrictLayout` (`characters`), because the client has no copy of `content/`. No row means no character yet: the server sends `appearance: null` and the creator opens after the welcome screen and cannot be dismissed. After that, clothes change only at home (`not_at_home` anywhere else) and only to free starter items (`not_owned` otherwise) until the shop exists. The creator is a DOM sheet over a camera close-up of your own character (no second 3D canvas, which would double GPU memory), set in a bedroom built around them (the [wardrobe screen](plans/slice-11-wardrobe.md): the street is hidden but keeps simulating, `Lighting` switches to fixed indoor light, and the camera cuts under a fade, because a glide would pass through the walls); every tap previews locally, and only Done sends `setAppearance`. Bodies are shown as "Body 1"/"Body 2" with no gender label, and every hair and outfit must fit both (decided 2026-10-20; `loadContent` checks it). Hair is low cut or bald until 11f. A removed catalog id falls back to `defaults` for that slot, so retiring an option never breaks a player. The synced `PlayerPosition.appearance` carries the encoded code for Phase 5; nothing reads it yet. Skin swatches in the creator are the tone's tint times an approximate base skin colour (`BASE_SKIN` in `CharacterCreator.tsx`), not the real texture.
- **Close hairstyles are a scalp cap plus a painted pattern (Slice 11f-2).** Cornrows and fade share one cap per body (`assets/blender/hair_cap.py`: a sphere shrink-wrapped onto that body's head and cut at a hairline set from the eyebrows; about 1.5k triangles, 8 KB). Its UVs are a top-down projection (u ear to ear, v forehead to nape, the crown at the centre), so a pattern is drawn on that square: `hairPatterns.ts` paints it in code (white hair, transparent scalp; no download), and the hair colour tints it, with `alphaTest` cutting out the scalp. A hair entry with a `pattern` uses this path. The cap is not skinned: it is parented to the `Head` bone with the matrix `boneInverse(Head) x bindMatrix x cap`, which moves it exactly like vertices weighted 100% to the head, so it never slides; this skipped re-skinning in Blender, which can change bone orientations. A new close style is a new pattern, not a new model; a style with volume (afro, puff, locs) needs its own skinned mesh like the pack hair.
- **Ankara prints and the dress (Slice 11f-3).**
  - **Prints.** An `outfitColours` entry may carry a `print` (a motif from `ANKARA_MOTIFS` plus 3–4 colours). `ankara.ts` paints it in code onto a 128 px tile made of whole cells, so it repeats without a seam (a test checks every motif), and nothing is downloaded. The body shader paints it on the outfit's `chosen` regions, sampling the tile with the body's own texture coordinates repeated `PRINT_REPEAT` (6) times; `fixed` regions stay plain. The cut edges of the body texture's pieces show as seams in the print, which is accepted at street distance. A print's `colour` is its main colour, for anything that cannot show the pattern. One texture per print, shared by everyone wearing it. The motifs are our own designs; never copy a real wax print (Vlisco and others are copyrighted).
  - **The dress.** An outfit may have a `piece` (a model per body), worn over the painted regions. The dress's skirt (`assets/blender/dress_skirt.py`) is shaped from each body's hips and legs: the outline of both legs together, never narrowing on the way down, flaring toward the hem; about 1k triangles and 4 KB per body. It is not skinned in Blender: `skirtWeights` (`skirtSkin.ts`) gives it weights in code, the waist on the pelvis and the hem following the nearer thigh up to 80%, and it binds to the body's own skeleton. That avoids sending the skeleton through Blender, which can change bone orientations. The legs can still show through the skirt in a big stride; the thighs under it are painted with the same print, so a glimpse reads as cloth. Its texture coordinates are in metres over a 0.36 m tile, matching the motif size on the painted top. One more draw call for anyone in a dress.
  - **Character models must reach the client.** `buildDistrictLayout` sends only the models a district uses, plus every hair part and garment piece in the character catalog. A new kind of character model must be added there too, or the client never loads it (no error: the part is simply missing).
- **Clothes are painted on, not modelled (decided 2026-10-18).** The free bodies come unclothed. The pipeline bakes a region mask per body (each texture pixel labelled torso, thigh and so on, from its strongest bone; `BODY_REGIONS` in `packages/shared/src/bodyRegions.ts`), and the body shader paints an outfit colour per region (`bodyMaterial.ts`). This only does close-fitting clothes; dresses, agbada and gele need modelled pieces. Every outfit must cover `torso` and `hips`, or the underwear painted on the base texture shows.
- **The superhero build is softened in code (decided 2026-10-18)** by scaling bones at load time (`BODY_SHAPE` in `Character.tsx`: slimmer chest, arms and thighs). This works only because the pipeline strips scale tracks from the clips. Tune it by eye on the phone.
- **Animation clips keep only bone rotations, plus the pelvis's offset from rest.** They were recorded on a mannequin with different proportions, so its bone positions would stretch our bodies. `clipsForBody` adds each body's own pelvis height back. Walk and run clips play at a rate that follows the character's speed, times a per-gait `CADENCE` (`animation.ts`). An exact ground match made the run look like hopping on the phone (2026-10-18), and quicker steps still looked like the legs went too far apart (2026-10-21): the pack's only run is a 5.4 m/s jog with long strides. Since 11g a second copy of the idle clip plays under the run at a quarter of the pose (`RUN_STANCE_MIX`, `runStanceWeight`), which shortens strides and arm swing, and the run plays 1.25x quicker than a ground match at that shortened stride (`CADENCE.run`), with its hip bounce halved around the average height (`RUN_BOUNCE`, `calmBounce`), because the exact match still looked like a little hop. Raise `RUN_STANCE_MIX` for a tighter run (0.35 is about the most before it looks like shuffling). The mix must come from the idle clip: a run weight below 1 would be filled from the rest pose, a T-pose. The work clip is "talking on the phone" (`work_phone`) for every job; per-job clips can come from job content later.
- **Building models (Slice 11b).** `content/models/catalog.json` is generated by `pnpm assets` (each model's measured footprint, height, triangles, bytes); never edit it by hand. It lives in `models/`, not `cities/`, because the loader reads every file in `cities/` as a city. A building's `model` must fill its footprint (at most `MODEL_OVERHANG_METRES` bigger, at least `MODEL_MIN_FILL` of it per axis, after `rotation` and `scale`), or the server refuses to start. The `district` message is a `DistrictLayout`: the config plus only the catalog entries it uses. Pack models come at arbitrary sizes, so a building's `scale` is chosen for human proportions (a floor about 3 m: KayKit ×5, Kenney Commercial ×7.5, Kenney Suburban ×7) and its footprint is then sized to the scaled model, never the other way round (stretching a model to a box makes giant doors). Buildings without a model are painted boxes with a zinc roof and windows (`world/windows.ts`) that light at night, with most going dark in a power cut except about a third of buildings "on generator". Since 11f-4 every Yaba building has a model, so the box is only the stand-in while one downloads; model windows go dark in a power cut by the same "on generator" rule (`modelWindowsLit`).
- **Model windows glow at night (2026-10-19).** The pipeline records where each model's window glass sits on its pack's colour sheet (`windows` in the catalog, from `KAYKIT_GLASS` and `KENNEY_CITY_GLASS` in `build.mts`). At load, triangles painted from glass are flagged by their centre (Draco rounds texture coordinates, so corners on a cell edge are unreliable), and a few lines added to the building's Lambert shader make them glow (`world/windowGlass.ts`). No extra draw call. A model's glass lights as a whole: all of it on an ordinary night, only for the "on generator" buildings in a cut (`modelWindowsLit`, the same hash as the boxes). The glass cells were found by measuring and checked by eye: KayKit's glass is the streaked grey square in the bottom-left quarter (its blue-grey cell is wall paint on the four-storey block, and glowed whole walls at first). **A new building model needs its glass cell checked at night**, or its walls may glow.
- **Night is brighter, a power cut darker (play-tested 2026-10-19: night was too dark on the phone).** `NIGHT` in `world/sky.ts` lights the street enough to see where you walk; when NEPA takes light at night the look blends toward `BLACKOUT_NIGHT` (half the light), so a cut still reads.
- **Street props (Slice 11c).** Prop kinds live in `content/props/kinds.json`; districts place them by kind. Lagos-specific props (generators, kiosks, container shops, electric poles, palms, billboards, hawker tables, plastic chairs, speed bumps) are built in code from boxes (`world/propShapes.ts`) and join the world's single `Boxes` draw call; generic ones (trees, planters, a bench, a bin, umbrellas) are pack models, one instanced mesh per kind. A kind's `blocks` is `"footprint"`, `"none"` (walk over or under) or a smaller box (a trunk, a pole); the server refuses a box bigger than what is drawn. Billboard and shop text is `label` in the city file, painted on a canvas (place flavour, so not in `en.json`); billboards advertise made-up brands only. Wires are one `LineSegments` call. Measured in desktop Chrome (2026-10-19, production build): 38–42 draw calls, ~47–54k triangles; not yet measured on the vivo Y29.
- **Labels face +z (11f-4).** The street camera always looks north (-z), so a painted label (billboard, kiosk, container shop, signboard) can be read only on a prop facing +z (rotation 0). The signboards (built shape `signboard`, two posts and a board, 2.8 m wide) carry place names by the buka, the church and the fuel station's prices.
- **Our own Lagos buildings (11f-4).** The buka, fuel-station shop, bus shelter, market and church are Blender-script models (`assets/blender/`, 150 to 2,400 triangles, 5–12 KB each), so no building in Yaba is a painted box any more. Their glass is the palette's `window_glass` swatch, which `pnpm blender` records in `assets/built/palette.json` and `pnpm assets` writes into each model's `windows`, so it glows at night like the pack buildings. Buildings south of the main road face it (rotation 180), so the camera mostly sees their backs and roofs; roofs carry the detail (corrugated zinc, rust patches, a red church roof with a gold cross). The fuel station's canopy is a prop (`fuel-canopy`) whose `blocks` box is its pump island: the pillars and pumps stand on the island, so you walk under the roof and stop only at the island.
- **Occlusion fading (11f-4).** The camera sits high and south of the player, so a tall building just south of them (the 10 m church above all) used to hide them completely. Each model building tests its footprint box against the line from the camera to the player's chest every frame (`world/occlusion.ts`) and is dithered out while it is in the way: its shader skips 70% of its screen pixels in a fixed 4x4 pattern (`addBuildingEffects` in `world/windowGlass.ts`). Real transparency was tried first and froze the vivo Y29 for 2.8 s (2026-10-20): switching a material into the transparent pass needs a different shader, and compiling a shader mid-game stalls a phone. The dither lives in the one shader every building already uses, so fading compiles nothing. **vivo Y29 after the fix (2026-10-21, production build): low 60 fps, worst frame 24 ms, dpr 1.50, 26 draw calls, 35.1k triangles, street 100%**, back to the 11e baseline. Its cost: the shader contains `discard`, which stops some mobile GPUs from skipping hidden building pixels early; the buildings are a handful of draw calls, so this is small. Every model building has its own materials (`withOwnMaterials`). Props (trees, billboards) do not fade yet. **Rule: never toggle `transparent` (or anything else that changes a material's shader) during play; anything that must change at runtime goes through a uniform.**
- **Hardening (Slice 11g).**
  - **Budgets fail loudly.** Each district's models (what `buildDistrictLayout` sends: placed models plus every hair part and garment piece) must stay within `DISTRICT_DOWNLOAD_BUDGET_BYTES` (6 MB), or the content check refuses to start the server. `public/assets/characters/` must stay within 1.5 MB, or `pnpm budget` fails. At 11g, Yaba's models were about 0.4 MB and the characters 0.67 MB. Ground, roads and prints are painted in code, so they cost nothing here.
  - **Shader warm-up.** `ShaderWarmUp` calls `renderer.compileAsync(scene, camera)` four times in the first 4.5 s, so every material (including buildings far out of view, and the street hidden behind a new player's creator, via the `warmUpWhileHidden` flag) compiles at load instead of when it first comes into view. A material that first appears later (a walker in a new outfit after warm-up) can still compile late; the `?fps` meter then shows "⚠ late shaders N". The warm-up also uploads every texture held in a material's slots (`renderer.initTexture`). Textures held only in shader uniforms (the people's region masks and prints) still upload on first draw: about 20 when a new player leaves the creator, 26 ms on desktop Chrome (2026-10-21), so check that frame on the phone. `shaderCache.test.ts` checks that building and body materials share one shader each.
  - **Adaptive quality and app switches.** `QualityGovernor` used to read the gap while the page was hidden as seconds of low fps and halve the street for good after any app switch of 5 s or more. It now pauses on `visibilitychange`, like the fps meter.
- **Traffic and walkers live only near the player (Slice 11h-5, 2026-10-22).**
  - **How it works.**
    - Each lane and walkway gets a window: its stretch inside a box around the player (`TRAFFIC_REACH` 115 m ahead, 55 behind, 100 to the side; `WALKER_REACH` 55/50/50). The box moves when the player crosses a 16 m area cell (`setTrafficWindow`, `setWalkerWindow`).
    - A vehicle past its lane's window parks. A parked one rejoins at the window start of whichever of its fleet's lanes crosses the window and is clear (`Vehicle.lanes`).
    - A walker who walks out comes back at the edge of a walkway crossing it, walking inward.
    - The windows are wider than what is drawn (`DRAW_REACH`, and 40 m for people), so nobody sees anyone join or leave.
    - The first window spreads everyone through it, so the street is busy from the start.
  - **The pool:** 39 vehicles and 16 walkers serve the whole district, so a 1 km Yaba costs no more.
  - **Busy areas** (`traffic.busyAreas` in the city plan: the junction, the motor park and Tejuosho, Sabo) get the schedule's full share. Elsewhere it is `calmShare` (0.6, in `traffic/kinds.json`).
  - **Junctions:** still the overlap of every pair of roads (`roadOverlaps`), worked out once at load: 18 roads is 153 pairs. A road graph waits for 11i, which needs one for routes anyway.
  - **vivo Y29 (2026-10-22, production build): 60 fps, low 58, worst 50 ms at 12 s, no hitch, dpr 1.50, 21 calls, 41.4k triangles, street 100%.** That is back in line with the pre-11h baseline, for a district 25 times the size.
  - **Cost:** concentrating everyone around the player made people the main triangle cost. Headless at the busy junction: 49 draw calls and 109k triangles with 16 walkers (58 and 135k with 30); 28–38 calls elsewhere. The phone reading decides whether the pool shrinks again.
  - **Fewer allocations:** `pointOnLane`, `projectOnLane` and `walkerPose` take an `out` object, so the per-frame loops allocate nothing.
- **vivo Y29 after 11h-4 (2026-10-22, production build, `?fps`).**
  - **First reading:** 44 fps, low 33, worst 110 ms.
  - **Diagnosis:** with the `?fps` switches (`diagnostics.ts`), the steady cost was the bones of 50 mounted people (20 NPCs, 30 walkers). three.js recomputes every object's matrices each frame, hidden or not.
    - `skipWhileHidden` now makes a hidden person skip their whole subtree.
    - Rule: anything mounted but usually hidden that has many children gets `skipWhileHidden`.
  - **After the fix, all at 60 fps:**
    - standing: low 43, one 219 ms hitch at 31 s, 42 calls, 45k triangles;

    - `dpr=1`: low 57, worst 35 ms, the same as dpr 1.5 (so the GPU is not short of fill rate).
  - **The remaining standing hitch** had no shader or texture work, which suggests a garbage-collection pause. The traffic stopped allocating every frame (reused math objects in `placeVehicle`, lane lists made once and sorted in place); the phone reading after that is still to take.
  - **Meter:** it now shows when the worst frame happened and how many frames took over 100 ms (`worst 219 ms at 31s · 1 hitch`).
- **The map and "walk there" (Slice 11i-1, 2026-10-22).**
  - **The map.**
    - Drawn on 2D canvases from the district header (every road and building outline, whatever chunks are loaded), north up like the street (`game/map/mapPaint.ts`).
    - The ground, roads and buildings are painted once into a base image (1.5 px a metre, about 950 px a side). Each redraw copies the visible part and adds the route, place dots, labels and the player.
    - The minimap (bottom right, about 190 m across, 5 redraws a second) opens the full map: drag, pinch or scroll to zoom, tap for a route.
    - No GPU cost and no new dependency.
  - **Routes.**
    - `routeBetween` (`packages/shared/src/roadGraph.ts`) turns the roads into a graph (nodes at crossings and road ends) and runs A*. A route keeps to the right-hand side of each road, 0.8 m in from the edge, or the middle of a narrow lane.
    - Nothing solid may stand on a road, so only the first leg (to the road) and the last (from the road) can meet a wall.
    - `planRoute` drops the last leg when a building outline stands in its way (a yard behind a shop), ending at the roadside.
  - **"Walk there".** A `RouteFollower` steers through `MoveInput` like a pushed joystick, so the server moves the player as for any walking.
    - Touching the joystick or keys takes over.
    - It ends "arrived" within 1 m of the end, or "stuck" when it gets less than 0.4 m closer to the next waypoint in 1.5 s. Pushing into a wall slides you along it, so "not moving" would miss that.
    - The route is a yellow strip on the road (`RouteRibbon`): one draw call, always mounted and warmed up, hidden without a route.
  - **First play-test fixes (vivo Y29, 2026-10-22):** walking a route ran at 60 fps (low 37, 34 calls, 55.3k triangles), but there was one 497 ms hitch. Timing headless runs traced it to the tap that picks a route, which had two costs:
    - **A shader finishing its compile.** The route strip's plain material was the only one of its kind, hidden until the first route. The warm-up starts compiling such a shader, but without parallel compiling it finishes on the first draw (`getProgramInfoLog`, 109 ms in software GL). The strip now draws a tiny stand-in under the ground from the start.
    - **A whole-scene re-render.** The route was React state at the top of `Game`. It is now a `RouteStore`, so only the strip, the minimap and the map re-render.
    - **Rule:** anything that first appears mid-game must share its material setup with something drawn from the start, or be drawn from the start out of sight. Warming a hidden object is not enough.
  - **After the fixes (vivo Y29, 2026-10-23, Next.js 16.4.2, night):** 60 fps, low 46, 33 calls, 60.1k triangles, no hitch on picking routes.
    - The one hitch left is 200 ms at 6 s (+21 textures): the people's painted clothes, uploaded on their first draw as the street finishes loading, just after the meter's warm-up.
    - It is once per load, so it is left as is. Uploading them earlier would only move the stall.
  - **Not done:**
    - The first leg can still meet a wall if the player starts inside a compound; the walk then stops as "stuck".
    - Routes ignore the traffic, which stops for the player anyway.
- **Chunk streaming and area of interest (Slice 11h-4, 2026-10-22).**
  - **What a client is sent.**
    - On join: the `district` header (`districtHeader` in `packages/shared/src/chunks.ts`). It holds the places, roads, road furniture (speed bumps, which the traffic needs from the start), traffic lanes, catalogs, NPCs, every building model with its count, and an outline map of every building for 11i.
    - Then the 5×5 chunks of 64 m around the player.
  - **While walking:**
    - When the server's position enters another chunk, `ChunkStream` sends only the chunks the player lacks.
    - Client (`ChunkStore`) and server both forget chunks more than 3 from the latest centre, by the same rule. Stepping back one chunk re-sends nothing; two re-sends the dropped edge.
  - **Sizes (JSON):**
    - the join is 114 KB (a 42 KB header plus 72 KB of chunks), down from 253 KB;
    - each chunk crossing is about 11 KB.
  - **The client:**
    - It rebuilds its loaded layout (`useLoadedDistrict`) and collision grid as chunks arrive.
    - Every building model kind and prop kind is mounted and warmed from the header, so a chunk arriving never downloads a model or compiles a shader.
    - Mesh capacities grow in doubling steps and never shrink (`roomFor`).
    - The traffic and walkers run on the header alone, so they never restart.
  - **NPCs stay in the header, not in chunks.**
    - When they streamed in, the first NPC of a new look (the YabaTech student's cornrows) compiled a shader mid-walk, and every NPC's character was rebuilt on each batch.
    - The client now caches each NPC's resolved look by id, and palms and billboards take their randomness from where they stand and what they say, not their place in a list.
    - Fine at a few dozen NPCs; a district with hundreds needs a warm-up for every character variant before NPCs can stream.
  - **Content check:** nothing may reach more than 64 m from its centre. Anything that touches the player's position then belongs to a chunk next to theirs, always loaded, so client collision never misses a wall.
  - **Players:** synced per client through Colyseus `StateView` (`players: t.map(PlayerPosition).view()`). Each client sees itself and the players within 80 m (`updateViews` every tick). Tested by moving a player 350 m away on the server.
  - **Measured.** Headless software GL, same route as 11h-3's measurement.
    - Draw calls and triangles are unchanged (22–41 calls, 43–70k triangles).
    - The worst frame is 112 ms against 67 ms in 11h-3.
    - A page-side timeline showed no shader compiles and no texture uploads in it, and only one JavaScript task over 50 ms after load (58 ms, at the first chunk batch). The rest is GPU-side buffer refills, which software GL exaggerates.
    - The vivo Y29's worst-frame reading decides whether chunk arrival needs smoothing (for example, per-chunk caches of slabs, fronds and labels instead of re-deriving from the whole loaded layout).
- **Only the area around the player is drawn (Slice 11h-3, 2026-10-22; `world/area.ts`).**
  - **How it works.**
    - At load, everything is bucketed into 64 m chunks (`ChunkIndex`, over the shared `SpatialGrid`).
    - When the player crosses into another 16 m area cell, the world refills its instanced meshes with the things nearby. That covers the plain-box mesh, the windows, one mesh per building model, one per prop model, the palm fronds and the vehicles.
    - Each kind stays one draw call, sized once for every copy in the district (`capacity`), so a refill only rewrites numbers and never builds a mesh or compiles a shader.
    - We chose this over one mesh per chunk, which would multiply draw calls by the number of chunks on screen.
  - **What is drawn where.**
    - The drawn area reaches 90 m ahead (north), 30 m behind and 75 m to each side. A portrait phone's camera sees almost to the horizon ahead and little behind.
    - Model buildings are full models within 60 m ahead and 50 m to the side, and plain boxes beyond (LOD).
    - Painted labels are drawn within 40 m. Their canvases are cached, so walking back never repaints them.
    - NPCs are hidden past 90 m.
    - The roads are one merged mesh, and the ground repeats a seamless 180 m tile (painted blobs wrap round its edges).
  - **Haze:** the fog now runs from 35 to 100 m from the camera (it was 50–140), and the camera's far plane is 105 m.
  - **Building models are instanced per kind.**
    - Their occlusion fade and window light became per-copy instance attributes (`instanceFade`, `instanceLit` in `addBuildingEffects`) instead of per-building uniforms. Every model building now shares its kind's materials (no more `withOwnMaterials`).
    - Only buildings within 35 m are tested for hiding the player.
    - A kind with nothing near is warmed up while hidden (`WARM_UP_WHILE_HIDDEN` on each instanced mesh), so the first one to come near compiles nothing.
  - **Traffic:** the simulation still runs every vehicle in the district (11h-5 changes that), but only those in the drawn area take an instance slot.
  - **Measured.** Headless Chrome with software WebGL (SwiftShader) on a Mac, production build, a 430×860 portrait window. The same 70 m walk north from spawn, then east:

- **Standing NPCs (Slice 11c)** are city-file entries (`npcs`: look, pose, spot, facing, optional `says` bubble) drawn with the player's `Character` holding one looping clip (`pose`). They block the player (decided 2026-10-19) but are not synced: they never move.
